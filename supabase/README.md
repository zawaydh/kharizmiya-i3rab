# Supabase schema

## قاعدة الإنتاج الحالية

لا تُشغّل `schema.sql` على قاعدة البيانات العاملة.

شغّل مرة واحدة فقط:

- `migrations/20260803_production_schema_hardening.sql`
- `migrations/20260805_server_authoritative_progress.sql`
- `migrations/20260806_error_observability.sql`

شغّل الملفات بالترتيب. الأول يوحّد جدولي التقدم والطلاب ويثبت القيود والتواريخ القديمة. الثاني يلغي كتابة الطالب المباشرة إلى جدول التقدم ويجعل الحفظ يمر من مسار الخادم الموثوق. الثالث ينشئ `app_error_events` لتسجيل أخطاء الواجهة من مسار الخادم فقط، مع RLS ومنع كل منح العميل. لا يحذف أي منها سجلًا محفوظًا.

بعده شغّل:

- `verify_current_schema.sql`

وهو فحص قراءة فقط يعرض الأعمدة والفهارس والسياسات، ثم يرمي خطأً صريحًا إذا وجد عمودًا أو فهرسًا أو RLS أو سياسة أو منحة أو قيمة غير سليمة. للتشغيل الآلي اضبط `SUPABASE_DB_URL` ثم نفّذ `npm run verify:supabase`؛ لا يضع المشغّل كلمة المرور في معاملات العملية.

يحتاج مسارا `/api/progress` و`/api/client-errors` إلى `SUPABASE_SERVICE_ROLE_KEY` في بيئة الخادم. لا تبدأ اسم هذا المفتاح بـ`NEXT_PUBLIC`، ولا ترسله إلى المتصفح. يعيد مسار الأخطاء `503` إذا تعذر التخزين بدل الإبلاغ عن نجاح وهمي، ويحذف من الخادم الأحداث الأقدم من 30 يومًا عند أول حادثة بعد كل نافذة يومية. ويمكن مراجعة الأحداث من محرر SQL أو لوحة Supabase بحساب إداري؛ لا يملك `anon` أو `authenticated` حق قراءتها.

> إذا سبق أن شغّلت `add_certificate_earned_at.sql` فلا مشكلة؛ الترقية النهائية تستخدم `if not exists` ولا تعيد كتابة تاريخ شهادة موجود.

## إنشاء مشروع Supabase جديد

استخدم ملفًا واحدًا فقط:

- `schema.sql`

وهو المخطط المرجعي المتوافق مع القراءة المباشرة للطالب والحفظ الموثوق من الخادم.

## الترقيات التاريخية

الملفات الأقدم في `migrations` محفوظة كسجل للتطوير السابق. لا تشغّلها بعد الترقية النهائية، ولا تعتمد عليها لإنشاء قاعدة جديدة من الصفر.

لا يستخدم التطبيق جدول `topics` في قاعدة البيانات؛ تعريف الموضوعات موجود داخل ملفات المشروع.
